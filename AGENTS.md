# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Purpose, commands and layout: `README.md` (a map; each folder's README has the details). The model: `modules/<id>/` (manifest, module adapter on the redaction contract, one `dataset-adapters/<dataset>.json` per dataset it runs) × `datasets/<id>/` (manifest, expected output contract `contract.json`, data or `loader.ts`); `engine/registry.ts` computes the grid from those files alone. `modules/README.md` and `datasets/README.md` have the formats and the add-a-module / add-a-dataset steps.
- `npm run check` (typecheck, ESLint, Prettier check, Knip, `npm test`; no model, no network) must pass before every commit. README "Code checks" has the conventions: Prettier only on its `package.json` globs (never Markdown docs, data files or `results/`), lint rules turned off only in `eslint.config.js` with a reason, new script or worker entries in `knip.json`, JSDoc beside symbols as the source of truth. Tests sit next to their code (`*.test.ts`).
- A dataset never maps labels for a module: each module's adapter maps its output onto the dataset's contract and lists the labels it cannot produce under `missing` (`npm run validate -- --adapters`). A run scores the labels the module maps; comparisons use the labels both map. Keep insusty-privacy's literature adapters equal to the maps its published scores used. A dataset contract change is a version bump; a manifest's `resultsId` keys cached outputs and runs: never change it.
- The default extension ref is `main` (`DEFAULT_EXT_REF` in `modules/insusty-privacy/ref.ts`); results are cached per commit sha, so a new `main` commit means a fresh run.
- Never modify the extension clone: refs are read with `git archive` into `cache/module/<sha>/` by the one materializer (`modules/insusty-privacy/materialize.ts`), and every runner scores them only through the redaction contract (`contract/`, `modules/insusty-privacy/insusty.ts`). The clone path comes from the untracked `bench.local.json`, `INSUSTY_EXT_REPO` or `--ext-repo`; never commit an absolute path.
- Inference must stay on onnxruntime-web WASM with default session options (`onnxruntime-node` is aliased in `package.json`). Native ORT and other graph-optimization levels change greedy outputs on the q8 models, so results would not reflect the extension.
- Models run one at a time, each in its own child process (`engine/workers/model.ts`); SmolLM2-360M peaks near 2 GB RSS while loading on a 7 GB machine, so never run two workers in parallel.
- `modules/insusty-privacy/runtime/transformers-loader.ts` mirrors the extension's `src/model-worker.ts` adapters; when a ref changes that worker, update the loader.
- `npm run dashboard` (`dashboard/`) writes no results and starts at most one bench process: the Grid's Run button runs `npm run bench -- --module --config --dataset` as a child (`dashboard/launcher.ts`), refuses while another bench run is active, and starts a paid (connected) configuration only after its plan and an explicit confirmation. It watches runs through `cache/active-runs/`, `/proc` and the result caches, and rebuilds plans with `engine/plan.ts`, the same planner the runners use; keep planning logic there, not in a CLI. Its Playground runs at most one model, in a child process killed on unload/switch (`dashboard/playground/`).
- Prompt/model iteration happens in `npm run lab` (`modules/insusty-privacy/lab/`, its README): named configs in `lab/configs.ts` are `ref` + overrides and results are cached by rendered prompt, so add new configs instead of editing ones `lab/experiments/LOG.md` cites. Keep `lab/experiments/LOG.md` and `REPORT.md` current after each experiment. Lab configurations are not grid rows.
- Shipped Local AI redaction improvements are tracked in `modules/insusty-privacy/shipped-improvements.md`, with the `shipped` lab baseline and one switch per improvement in `modules/insusty-privacy/lab/shipped.ts`. Whenever an improvement ships to the extension, in the same change: set it in `SHIPPED_CONFIG`, add its switch (a new id, never a changed meaning), add a ledger entry (PR URL, merge commit, evidence incl. held-out), and rerun `npm run ablate`. Measure new proposals against `shipped` (`npm run ablate -- --with <config>`); the ledger's "Rejected proposals" lists what was tried and failed, so check it first.
- The bench keeps two models, both configurations of insusty-privacy: `smollm2-360m` on the device (the ref's shipped model) and `glm47-flash-connected`; a new local model or connection setting is a new configuration id, never an edit. Older models, candidates and their results were deleted on 2026-10-17 to start fresh.
- The `test` split is held out: never tune label descriptions or prompts on it. `npm run split` only fills missing splits. In the lab, tune on `datasets/insusty-custom/sets/tune96.json`, confirm on `confirm48.json`, and use `heldout-test.json` (`--allow-test`) only for one-shot checks of choices already made on dev.
- This machine has ~7 GB RAM shared with other lanes: model runs go through the memory waits and guards (`engine/memory.ts`, used by the lab and the runners); keep ~1.5 GB free (when other lanes hold memory, `LAB_MEM_WAIT_S=3600` makes the lab wait instead of skipping the model after 180 s) and never kill processes you did not start (`pkill -f` patterns also match your own shell). Put scratch installs under `cache/tmp/`, not `/tmp` (tmpfs, eats RAM).
- insusty-builtin (`npm run detbench`, `datasets/insusty-builtin/README.md`) scores rule-based detection, no model. Ground truth uses the upgraded category names; map new ref category names in `CATEGORY_ALIASES` (`modules/insusty-privacy/labels.ts`), never rename dataset categories. Dataset values must stay fictional and checksum-valid (`--validate`), and secret-looking values raw-free (`--defang-dataset`) so secret scanners do not block pushes. A hard case found in an extension review becomes a tagged regression case there (or in the insusty-documents builders), and detector changes pass its gate (`--compare <base> --gate`). The extension's skills cite `npm run detbench -- --ref main --compare <branch>` and `docs/detbench.md`: keep both working.
- New experiments (a model, backend, prompt or setting) must be runnable from `npm run bench` (a grid cell) and viewable in `npm run dashboard` afterwards: write results in the shared formats the dashboard reads (`results/jobs/` + `results/runs/<name>/`, or `lab/experiments/runs/<name>.json` for the lab) and plan through `engine/plan.ts`. No one-off scripts whose results only live in logs.
- The connected configuration (`modules/insusty-privacy/connected.ts`, `--models glm47-flash-connected`, never part of `all`) runs through the ref's own connected-model client. Keys come only from the environment (`AWS_BEARER_TOKEN_BEDROCK`; never print, log or commit them); send only the fictional dataset. `--budget-usd` (default 5) caps all cached connected spend.
- The extension's "Trusted AI redaction" connected-model client is the source of truth: the bench runs the ref's own client (`modules/insusty-privacy/insusty.ts`) and supplies only the transport (`connected.ts`: reply cache, cost, budget); measurement concerns stay there, never request building or parsing.
- Results are cached by content hash in `results/jobs/` (machines from before the modules/datasets layout keep `runs/` and the old `cache/` folders, read through `engine/paths.ts` `kept`); rerunning with nothing new only rescores. Do not edit files imported by `engine/workers/model.ts` (or `modules/insusty-privacy/lab/` during `npm run ablate`) while a run is in progress (each model's worker, and each later lab call, is spawned later and would load the edited code).
